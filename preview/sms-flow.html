Step 01 — Photo received

Bot greets + asks for recipient name

Trigger: user texts an MMS photo. State: idle → awaiting_recipient_name.

Got the photo. Who's it for? Reply with their name.

Tightened from "Got your photo! Who's this postcard for?" Three small wins: drop the 2018-startup exclamation, drop "postcard" (implicit from context), and shorten "their name" prep work. 53 chars, fits a single SMS segment with room.

Step 02 — Name → address

Bot acknowledges + asks for full address

Trigger: user texts a name. State: awaiting_recipient_name → awaiting_recipient_address.

Got it, to Lori. What's their full address? One line works: "123 Main St, Naples FL 34101". We'll figure it out.

Removed two em-dashes (voice rule). "One line works" is more direct than "You can send it one line like." The reassurance — "we'll figure it out" — is the line that does the real work; the LLM parser is forgiving.

Step 03 — Address parsed

Bot reads back the parsed address, asks Y

Trigger: user texts an address (any format). State: awaiting_recipient_address → awaiting_address_confirm.

Mailing to Lori at 456 Ocean Dr, Naples, FL 34102. Reply Y to confirm, or send the right address.

Read-back de-risks bad LLM parses. "Right address" replaces "correct address" — less schoolmarmy. The Y is uppercase but the LLM accepts y/yes/ok/sure too; we don't need to explain that.

Step 04 — Confirmed

Bot asks for the message

Trigger: user texts Y / yes / ok / yeah sure. State: awaiting_address_confirm → awaiting_message.

What should the card say? Reply with your note. (Up to 240 chars.)

"Card" not "postcard" (implicit). The 240-char limit is in a parenthetical so it doesn't feel like a contract clause. The LLM also silently truncates anything past 240, so this is a soft cap.

Step 05 — Note saved

Trigger: user texts the note. State: awaiting_message → awaiting_sender_location (skips when profile already has city/state).

"Powers your live delivery map" sells the payoff — the user finds out their city becomes the start-pin on the /c/ confirmation page. "Just your" was filler. "Last thing" signals the end is near (anti-drop-off).

"For her birthday June 15."

The model resolves three things at once: that the user is scheduling (not asking a question), what date they mean, and that a future-arrival date implies a 7-day-earlier send date. We back-solve Lob's first-class transit.

Parse

Schedule intent → arrival ISO

Trigger: user texts schedule phrase at awaiting_send_confirm.

"for her birthday June 15"
"send in 3 days"
"mail it next Tuesday"
"send on the 15th"
"schedule June 15"

All resolve to a single arrival_iso via gpt-4o-mini with today in the system prompt. Then we subtract 7 days to get scheduled_send_at. Past dates → "too close, try later or SEND now."

Confirm

"We'll mail it on X so it arrives around Y."

Pros: the two dates remove ambiguity. The /c/ link works immediately (renders the "Mailing soon" state). Cons: "around Jun 15" is honest but slightly hedgy — Lob can vary. Could say "by Jun 15" for premium feel, but honest beats premium.

A regex match in sms-inbound short-circuits before the state machine. State is preserved. The user finishes their in-progress card after topping up.

Pack matrix

Three options. Membership pricing — premium, not utility.

BUY 5 → 4 cards / $5 / $1.25 per
BUY or BUY 10 → 10 cards / $10 / $1.00 per
BUY 25 → 30 cards / $25 / $0.83 per — for the regulars

Bare "BUY" defaults to p25 — the featured value pack at sub-stamp pricing. Anchored regex: "i want to BUY" doesn't match (intentional — let the user type the keyword explicitly).

Pipeline

Stripe Checkout → webhook → credits

sms-inbound regex match → sms-buy-checkout (internal secret gate) → finds/creates profile + Stripe customer by phone → creates Checkout Session with metadata → returns hosted URL.

Same webhook (stripe-webhook) that handles iOS PaymentSheet purchases credits the user — same RPC apply_stripe_credit_purchase. One credit pipeline, two surfaces.

Nudges

2. Last-card-sent post-mail: "Mailed! 📮 … That was your last card — reply BUY 5 ($5)…"

QA stress test — what we just fixed.

~50 unique test phones pummeled sms-inbound. Cleaned-up afterward. Bugs found, severity-sorted. Fixes applied in this same review round.

Bug · Fixed

"first card free" was shown to everyone

Was: hard-coded in handleMessage and handleSenderLocation. A user with credits > 1 still saw "(first card free)" on every card.
Now: branched on profile.credits. New users (no prior sends) → "First one's free." Repeat senders → "Uses 1 of N cards."

Bug · Fixed

"BUY 100" / "BUY MORE" got the generic idle reply

Was: the regex ^BUY\s*(5|25|50)?$ didn't match BUY-with-unknown-size, falling through to the per-step state machine and ultimately the idle prompt. A user typing "BUY 100" is showing strong intent and got "Send a photo to get started."
Now: a second regex ^BUY\b catches the typo/unknown-size case and replies: "BUY 5 ($5), BUY 25 ($20), or BUY 50 ($35). Or text BUY for our featured 25-pack."

Bug · Fixed

"yeah sure" at address-confirm was treated as unclear

Was: fast-path regex was ^yeah$, multi-word affirmatives fell through to the LLM, which also said unclear.
Now: fast-path expanded to multi-word: "yeah sure", "yes please", "sounds good", "looks good", "go ahead", "sure thing".

Bug · Fixed

Schedule rejection was silent on "too close" dates

Was: "send tomorrow" and "send in 1 day" returned the generic "Reply SEND or schedule it..." with no acknowledgment that we'd parsed a date and decided it was too soon. User had no signal that lead time, not parsing, was the issue.
Now: LLM is instructed to return intent: "schedule" with arrival_iso EVEN for too-close dates, then doSchedule rejects with a specific message: "May 27 is too close — we need ~7 days lead time. Reply SEND to mail now, or pick a later date."

Note · Accepted

BUY / CANCEL / STOP at recipient-name step steals the input

A friend literally named "Buy" or "Stop" cannot be entered as a recipient name. Decision: accept this. Reserved keywords are a feature — BUY needs to interrupt mid-flow for top-up, CANCEL needs to work from any step. The "friend named Buy" case is ~10⁻⁶ rare and the user can type "send to Buy at 123 Main..." in the future address freeform. Worth a docs note.

Note · Documented

STOP overlaps with TCPA opt-out keyword

Twilio intercepts STOP at the carrier layer for SMS unsubscribe — our function never sees it on a real STOP. Our handler only fires for the typo case (STOP + period, "STOPPP" etc., which don't match Twilio's exact match). Documented; no fix needed.
