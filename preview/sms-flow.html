13 messages. ~90 seconds.

A first-time sender goes from "what is this number?" to a real paper postcard mailed to a real friend without ever leaving Messages. That's the whole game.

Step 01 — Photo received

Bot greets + asks for recipient name

Trigger: user texts an MMS photo. State: idle → awaiting_recipient_name.

Got your photo! Who's this postcard for? Reply with their name.

Pros: conversational, low friction, asks for the most important thing first. Cons: the exclamation is a little 2018-startup. "Postcard" appears twice ("postcard for" + the implicit context).

Step 02 — Name → address

Bot acknowledges + asks for full address

Trigger: user texts a name. State: awaiting_recipient_name → awaiting_recipient_address.

Got it — to Lori. What's their full address? You can send it one line like "123 Main St, Naples FL 34101" — we'll figure it out.

Pros: "we'll figure it out" is reassuring — the LLM parser handles messy input. Cons: two em-dashes in one message. Voice rule violation

Step 03 — Address parsed

Bot reads back the parsed address, asks Y

Trigger: user texts an address (any format). State: awaiting_recipient_address → awaiting_address_confirm.

Mailing to Lori at 456 Ocean Dr, Naples, FL 34102. Reply Y to confirm or send the correct address.

Pros: the read-back de-risks bad LLM parses. "Send the correct address" is a clear escape hatch. Cons: the Y is uppercase but the LLM accepts y/yes/ok/sure too — that's not visible to the user.

Step 04 — Confirmed

Bot asks for the message

Trigger: user texts Y / yes / ok. State: awaiting_address_confirm → awaiting_message.

What should the postcard say? Reply with your note (240 characters max).

Pros: direct ask. The 240-char limit is shown so the user can plan. Cons: "240 characters max" feels engineery. Could be "(up to 240 chars)" or just omit the limit — the LLM truncates silently anyway.

Step 05 — Note saved

Bot asks where the user is

Trigger: user texts the note. State: awaiting_message → awaiting_sender_location (or skips to awaiting_send_confirm if profile has city/state).

Last thing: where are you texting from? Just your city + state (e.g. "Bethesda, MD"). Goes on the back as your return address.

Pros: "last thing" signals end is near (reduces drop-off). The example sets expectations cleanly. Cons: "goes on the back as your return address" buries the lede — the REAL reason we ask is to power the live delivery map on the /c/ confirmation page. Could say so.

Step 06 — Location captured

Bot summarizes + asks to SEND, schedule, or CANCEL

Trigger: user texts "Bethesda MD" / "SF" / etc. State: awaiting_sender_location → awaiting_send_confirm.

"For her birthday June 15."

The model resolves three things at once: that the user is scheduling (not asking a question), what date they mean, and that a future-arrival date implies a 7-day-earlier send date. We back-solve Lob's first-class transit.

Parse

Schedule intent → arrival ISO

Trigger: user texts schedule phrase at awaiting_send_confirm.

"for her birthday June 15"
"send in 3 days"
"mail it next Tuesday"
"send on the 15th"
"schedule June 15"

All resolve to a single arrival_iso via gpt-4o-mini with today in the system prompt. Then we subtract 7 days to get scheduled_send_at. Past dates → "too close, try later or SEND now."

Confirm

"We'll mail it on X so it arrives around Y."

Pros: the two dates remove ambiguity. The /c/ link works immediately (renders the "Mailing soon" state). Cons: "around Jun 15" is honest but slightly hedgy — Lob can vary. Could say "by Jun 15" for premium feel, but honest beats premium.

Cron

Daily 14:00 UTC, pg_cron fires Lob

pg_cron → pg_net HTTP POST → fire-scheduled-postcards Edge Function → list_due_scheduled_postcards RPC → atomic claim (status flip scheduled→queued) → Lob → status='sent'. On Lob failure: revert to scheduled, next tick retries.

BUY · BUY 5 · BUY 25 · BUY 50

A regex match in sms-inbound short-circuits before the state machine. State is preserved. The user finishes their in-progress card after topping up.

Pack matrix

Three options. Sub-USPS per stamp at the featured pack.

BUY 5 → 5 cards / $5 / $1.00 per
BUY or BUY 25 → 25 cards / $20 / $0.80 per — less than a USPS stamp
BUY 50 → 50 cards / $35 / $0.70 per

Bare "BUY" defaults to p25 — the featured value pack at sub-stamp pricing. Anchored regex: "i want to BUY" doesn't match (intentional — let the user type the keyword explicitly).

Pipeline

Stripe Checkout → webhook → credits

sms-inbound regex match → sms-buy-checkout (internal secret gate) → finds/creates profile + Stripe customer by phone → creates Checkout Session with metadata → returns hosted URL.

Same webhook (stripe-webhook) that handles iOS PaymentSheet purchases credits the user — same RPC apply_stripe_credit_purchase. One credit pipeline, two surfaces.

Nudges

Three places we surface BUY

1. Insufficient credits on SEND: "You're out of cards. Reply BUY 5 ($5)…"
2. Last-card-sent post-mail: "Mailed! 📮 … That was your last card — reply BUY 5 ($5)…"
3. Returning user idle: "You're out of cards. Reply BUY 5…"

Empty states + edge cases.

Six things a user might text that aren't a photo. We branch on whether they have a profile, whether they have credits, and what kind of restart command they're using.

First-time idle

No profile yet · texts "hi"

Send a photo to get started. We'll turn it into a real paper postcard — first one's free.

Most common entry. The "first one's free" carries the entire CAC argument.

Returning idle · has credits

Profile exists · credits > 0 · texts "hi"

You have 4 cards left. Text a photo to start a new one.

No friction. Tells them what's in the bank and what to do next.

Returning idle · 0 credits

Profile exists · credits = 0 · texts "hi"

You're out of cards. Reply BUY 5 ($5), BUY 25 ($20), or BUY 50 ($35) to top up, then text a photo to send a card.

Conversion moment. Three price points, all under $1/stamp at the featured pack.

Restart commands

CANCEL · STOP · RESTART · "nevermind"

Cancelled. Text a new photo when you're ready to start over.

Note: "cancel" here means "abandon the current draft." A draft-card cancel flow doesn't exist yet (would need to disambiguate which scheduled card). Worth thinking about post-A2P. Open question

New photo mid-flow

User texts a 2nd photo at any step

Got your photo! Who's this postcard for? Reply with their name.

Global short-circuit: a new photo always restarts. Previous draft is abandoned (no double-confirm). Reasonable for now — users who change their mind shouldn't have to type CANCEL first.
